# Order and licence contract — Torque ERP, ScanPlan and TAW

**Status:** implemented in the Torque ERP repository and the RAVBsoft portal.
**Scope:** the shared self-service order, provisioning, trial and activation flow for
all three products. ScanPlan and TAW keep their own codebases; this document is the
contract those builds must implement on the client side.

---

## 1. The flow in one picture

```text
Developer shares /start
        │
        ▼
Client chooses product + plan + (Torque ERP) modules, enters business details
        │  public anon RPC: submit_client_order(jsonb)
        ▼
Portal: Orders / Pending installations          status Submitted
        │  review the order, confirm the fee
        ▼
Provisioning                                     status Reviewing → Provisioning
        │  create Supabase + Cloudflare + other accounts
        │  give the deployment agent access
        │  choose installation ID, server address, owner login/password/PIN
        ▼
Deployment                                       status Deployed
        │  golden master deployed to the client's own accounts
        ▼
Handover                                         status Delivered
        │  send the app link, installation ID and initial login
        ▼
Client initial setup                             status Trial
        │  30 days, every feature unlocked
        ▼
Day 15 of the trial: daily activation prompt (24-hour snooze)
        │
        ▼
Payment received, developer activates from the portal   status Active
        │  paid period applied to developer_client_installations
        ▼
Client sees a one-time thank-you; access continues
with only the modules bought on the order
```

The order record and the client installation are linked by `client_id`
(`developer_client_orders.client_id → developer_client_installations.id`) and by
the installation ID stored on both rows.

## 2. Products and installation IDs

| Product | Portal product value | Installation prefix | Modules | Licence poll RPC |
| --- | --- | --- | --- | --- |
| Torque ERP | `Torque ERP` | `WS-LK-XXXXXXXX` | 11 feature flags | `poll_workshop_license` |
| ScanPlan | `ScanPlan` | `SP-LK-XXXXXXXX` | none — every feature | product-specific poll |
| TAW | `TAW` | `TAW-LK-XXXXXXXX` | none — every feature | `poll_taw_license` |

Rules:

- The installation ID is generated in the portal, not chosen by the client.
- The same ID must be written to the client's own database and baked into the
  deployed build (`VITE_TAW_INSTALLATION_ID` for TAW) before the first licence
  poll. The client never enters or selects a licence inside the app; the owner
  only signs in and completes initial setup.
- The public order page must never accept an arbitrary installation ID. It only
  records the requested product; provisioning assigns the ID.
- For ScanPlan and TAW, `modules` is always `[]`. Their activation unlocks the
  whole product. Torque ERP uses the flag list below.
- TAW's `poll_taw_license(p_license_key text)` resolves the `TAW-LK-*` installation
  ID first and returns `Trial` or `Active` from `developer_client_installations`;
  older `TAW-YYYYMMDD-XXXXXXXX` keys in `developer_license_keys` remain a fallback
  for installations issued before the order pipeline.

### Torque ERP module keys

```text
enable_multi_sections
enable_paint_module
enable_insurance_module
enable_estimates_module
enable_vat_invoicing
enable_advanced_accounting
enable_payroll_epf_etf
enable_daily_wages
enable_driver_commissions
enable_petty_cash
enable_voice_notifications
```

The RPC filters out unknown keys and rejects a Torque ERP order with no modules.
`src/lib/features.ts` is the single source of truth for labels and defaults.

## 3. Public order page (`/start`)

Implemented by `src/pages/StartOrder.tsx`.

- One link covers all products. The developer copies it from the portal header or
  the Orders panel.
- Required fields: business/workshop name, contact person, phone.
- Optional: email, district, address, notes.
- Product, plan and modules are selected on the page.
- Plan prices come from `src/lib/orders.ts`; ScanPlan is quoted after review.
- Submission calls the anon RPC `submit_client_order`. No payment is taken and no
  table is exposed to `anon`.
- If the master Supabase URL is not configured, the order is stored in this
  browser under `ravsoft_client_orders_v1` so the demo portal still shows the
  queue.
- The confirmation screen shows the order reference and the four stages:
  review, accounts/deployment, handover, activation.

### Order reference

`ORD-YYYYMMDD-XXXXXX` — generated by the RPC, unique, safe to quote to the client.

## 4. Portal pipeline

Implemented by `src/components/OrdersPanel.tsx` and wired into
`src/pages/DeveloperPortal.tsx` (first tab, **Orders**, plus the **Pending
installations** KPI).

Statuses and what the developer does:

| Status | Meaning | Next action |
| --- | --- | --- |
| `Submitted` | Order received from `/start` | Review details and fee |
| `Reviewing` | Fee/scope being confirmed | Create accounts |
| `Provisioning` | Supabase, Cloudflare, WAHA, other accounts, AI access | Record the checklist and deployment values |
| `Deployed` | Golden master built and published | Choose credentials and send handover |
| `Delivered` | App link and initial login sent | Client completes setup → `Trial` |
| `Trial` | Client installation running its 30-day trial | Activate after payment |
| `Active` | Paid period applied, purchased modules enforced | Renew before expiry |
| `Cancelled` | Order withdrawn | — |

The panel stores:

- provisioning checklist: Supabase, Cloudflare, WAHA/WhatsApp, other accounts,
  deployment-agent access, app deployed;
- deployment values: installation ID, server address, app URL, Supabase URL,
  Cloudflare project, optional deploy webhook;
- initial credentials: owner login, initial password, owner PIN; the developer
  can copy them and clear them after handover (`credentials_cleared_at`);
- handover helpers: copy message, WhatsApp, email, mark link sent;
- **Deploy now** posts the deployment brief to the optional webhook and marks the
  order deployed;
- **Register installation** creates/updates the `developer_client_installations`
  row with the same installation ID and the purchased module flags;
- **Activate** sets the client `Active`, writes the paid expiry, records a
  `developer_license_payments` row and copies the purchased flags onto the
  installation.

### Conversion rules

- A new installation starts as `Trial`; the trial expiry is
  `deliveredAt + trial_days` (default 30 days).
- Re-registering an existing `Active` client does **not** downgrade it to Trial.
- Activation never rewrites the client's data. It only changes licence fields.
- ScanPlan/TAW installations get every feature after activation. Torque ERP gets
  exactly the order's module keys.
- The order row keeps `status = Active` after activation so the pipeline and
  payment history stay auditable.

## 5. Client-side licence semantics

These rules must be identical in Torque ERP, ScanPlan and TAW.

### 5.1 Stored fields

On the client installation's settings row:

| Field | Purpose |
| --- | --- |
| `trialStartedAt` | Start of the 30-day trial (client initial setup) |
| `licenseStatus` | `Trial`, `Active`, `Expired`, `Suspended` |
| `licenseExpiresAt` | Paid expiry, or trial expiry when supplied remotely |
| `licensePlan` | `Lite`, `Starter`, `Growth`, `Pro`, `Enterprise` |
| `featureFlags` | Purchased module flags (authoritative after activation) |
| `licenseActivatedAt` | Set when the client transitions to `Active` |
| `licenceActivationAcknowledgedAt` | Set when the thank-you is dismissed |

Constants live in `src/lib/licenceConfig.ts`:

```ts
export const TRIAL_DAYS = 30;
export const OFFLINE_GRACE_DAYS = 7;
```

### 5.2 Trial = full access

`featureFlagsFor(settings)` returns **all flags on** while the installation is in
a valid trial, regardless of the stored flags. This is what makes the trial a
full-access trial. The same function returns the stored flags once the licence is
`Active`.

Consequences:

- Do not gate trial screens by purchased modules.
- Do not write the purchased flags into the runtime flag state during trial; keep
  them stored so activation can enforce them.
- Demo mode also unlocks everything.
- An expired trial, `Expired` or `Suspended` licence must not unlock everything.

### 5.3 Day-15 activation prompt

- Owner-only.
- Shown from day 15 of the 30-day trial (14 full days elapsed).
- Snooze for 24 hours (`torque_trial_activation_prompt_v1` in Torque ERP; use the
  product's own key).
- Copy: trial is still active, full access continues, activate to avoid
  interruption and keep the purchased modules.
- For Torque ERP, **Activate now** opens **Settings → Licence**. For TAW there
  is no licence form; the message explains that RAVBsoft activates the copy from
  the portal and the client takes no action.

### 5.4 One-time activation thank-you

Show when:

```ts
licence.mode === "Active" &&
settings.licenseActivatedAt &&
settings.licenceActivationAcknowledgedAt !== settings.licenseActivatedAt
```

On dismiss, set `licenceActivationAcknowledgedAt = licenseActivatedAt`. A later
renewal/activation with a new `licenseActivatedAt` shows the message once again.

The message:

- thanks the client and confirms the copy is activated;
- shows the paid expiry (or lifetime);
- lists the modules on the licence;
- confirms that data, users and settings are unchanged;
- points to RAVBsoft support with the installation ID.

### 5.5 Remote sync

- The client polls the portal outbound only. Never expose an inbound licence
  endpoint.
- A remote `Trial` with an expiry stays in `Trial` mode; it must not be promoted
  to `Active` just because the row exists.
- A remote transition to `Active` records `licenseActivatedAt` and clears
  `licenceActivationAcknowledgedAt` so the thank-you appears.
- Offline operation is allowed for `OFFLINE_GRACE_DAYS` after the last successful
  check, using the cached licence.
- A backwards clock forces a fresh online check.

## 6. Database objects

Migration: `supabase/migrations/20261126000100_client_orders.sql`.

- Table `public.developer_client_orders` — admin-only RLS
  (`public.is_portal_admin()`), no `anon` table privileges.
- Function `public.submit_client_order(p_payload jsonb) returns text` —
  `security definer`, executable by `anon` and `authenticated`, validates the
  payload, filters module keys, throttles duplicate phone/product submissions for
  five minutes and returns the order reference.
- Existing installation table remains the entitlement source:
  `developer_client_installations` (`status`, `expires_at`, `plan`,
  `feature_flags`, `last_seen_at`).
- Payments remain in `developer_license_payments`.

The migration is additive and idempotent. Apply it after `0001`–`0008`.

## 7. Porting the client behaviour to ScanPlan and TAW

Both repositories need the following, adapted to their own settings shape:

1. **Trial constants** — copy `TRIAL_DAYS` and `OFFLINE_GRACE_DAYS` into a shared
   config module.
2. **Trial full access** — every feature gate must consult a `featureFlagsFor()`
   equivalent that returns all-on during a valid trial and the stored flags after
   activation.
3. **Licence mode** — a remote trial with an expiry must report `Trial`, not
   `Active`.
4. **Activation timestamp** — when the remote status becomes `Active`, set
   `licenseActivatedAt` and clear the acknowledgement.
5. **Day-15 prompt** — owner-only, daily with a 24-hour snooze. Torque ERP links
   to its Licence screen; TAW only informs the owner that RAVBsoft will activate
   the copy from the portal.
6. **Thank-you** — one-time per `licenseActivatedAt`, listing the product's
   licensed features (ScanPlan/TAW: all features).
7. **Settings summary** — Torque ERP shows licensed modules in the Licence tab.
   TAW Settings is read-only workspace status; the installation ID comes from
   the deployment, not from a form.
8. **No order UI inside the client app** — orders live only on the portal and the
   public `/start` page.

ScanPlan and TAW do not use Torque ERP's module keys. Their activation is
all-or-nothing; keep `modules = []` in the portal order and ignore
`feature_flags` for enforcement.

## 8. Acceptance checklist

Portal:

- [ ] `/start` submits with the anon key and returns a reference.
- [ ] The order appears in **Orders** as `Submitted` and in the pending KPI.
- [ ] The developer can complete the checklist, deployment values and credentials.
- [ ] **Register installation** creates the client row with the same ID.
- [ ] A new client is `Trial` with a 30-day expiry and every module unlocked.
- [ ] **Activate** sets `Active`, writes the paid expiry, records the payment and
      keeps only the purchased Torque ERP modules.
- [ ] Re-registering an `Active` client does not downgrade it.
- [ ] Credentials can be cleared and disappear from the handover message.

Client:

- [ ] Fresh install starts a 30-day trial with full access.
- [ ] Day 15 shows the activation prompt once per day for the owner.
- [ ] After portal activation and sync, the thank-you appears once.
- [ ] Dismissing the thank-you never shows it again until a new activation.
- [ ] Torque ERP keeps only the purchased modules after activation.
- [ ] ScanPlan and TAW keep all features after activation.
- [ ] Expired/suspended licences lock the app and do not unlock modules.
